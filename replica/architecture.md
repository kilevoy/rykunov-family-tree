# Architecture: «Родословная Рыкуновых» — веб-клон ядра Genery «Древо Жизни»

Основа: `replica/recon.md` (источники [1]–[14] там), `replica/features.csv`. Для кого: семья Рыкуновых (Колок), личный инструмент, не на продажу.

## Ограничения, которые определяют решения

- **Репозиторий публичный** (GitHub Pages включён), а в дереве будут живые родственники и фото. Данные не хранить в репозитории и не на Pages. Код приложения можно держать в приватном репозитории или отдельной ветке без данных. [факт: репозиторий public по данным GitHub]
- Пользователей — единицы (семья), персон — сотни. Масштабирование не нужно; нужны приватность, простота и экспорт данных наружу (GEDCOM) как страховка.
- Совместный доступ в оригинале: общий аккаунт Яндекса, правка по очереди, «только чтение» для второго [recon 8]. Клон делает лучше: свои аккаунты, роли, уровень конфиденциальности по пользователю.

## Schema

17 таблиц, 2 представления; `replica/schema.sql` загружен в Postgres 16 без ошибок (проверено на пустой базе).
Access rules: **RLS** на каждой таблице. Доступ определяется членством в `tree_members` (owner / editor / viewer) и числом `max_privacy` (0–10): читатель видит только записи, где `privacy_level` не выше его `max_privacy`. Живых родственников ставьте с высоким `privacy_level`.

| таблица | зачем | аналог в Genery |
| --- | --- | --- |
| trees, tree_members, tree_invites | дерево, участники и роли, приглашения | облако + общий аккаунт [8] |
| persons | персоны | вкладка «Персоны» S01, окно S09 |
| event_types, events, event_participants | события и роли участников | S03, S20, [12] |
| families | «роды» | S07, [13] |
| places | места с координатами и прежними названиями | S05, [7] |
| sources, source_links | источники | S06, S12 |
| documents, document_links, photo_tags | файлы, привязки, отметки людей | S04, S11, S21, [7] |
| tasks | задачи исследователя | S08 |
| gedcom_imports | журнал импорта и отчёт о потерях | S23 |
| audit_log | кто что менял | нет в оригинале (добавлено) |

Ключевые решения:
- **Родство вычисляется из событий**, как в Genery: родители ребёнка — участники события «рождение» с ролями `father`/`mother`; супруги — участники «брака» с ролями `husband`/`wife`. Представления `parent_links`, `spouse_links`. Это [гипотеза] о внутреннем устройстве Genery, но она согласуется с руководством [6][12]; для клона это хорошая модель, потому что одно событие «брак» хранит и дату, и место, и свидетелей.
- **Ограничения в БД, а не в интерфейсе:** персона один раз на событие (PK); не более одного отца, матери и ребёнка в событии (уникальный индекс); `date_to >= date_from`.
- **Даты:** хранятся исходный текст (`date_text`), вид (`exact/about/between/…`), календарь (`gregorian/julian`) и дата для сортировки. Так не теряется «26(06).05(06).1799» из S14.
- **Одновременная правка:** вместо блокировки файла `.~lock` [8] — поле `version` и проверка при сохранении (оптимистичная блокировка). Два человека не затирают друг друга.
- Проверено на тестовой базе: второй отец в одном событии отклоняется; читатель с `max_privacy=5` видит 1 из 2 персон, владелец — 2, неавторизованный — 0.

Не покрыто схемой (решить при сборке): точные правила допустимости пола в ролях («мать не может быть мужчиной» [6]) — это проверка на уровне приложения; политики Storage (в конце файла описаны текстом, их надо создать в Supabase); `event_participants.tree_id` должен совпадать с деревом события — проверить триггером или в слое данных.

## API

Серверные действия Next.js (`/app/actions`) и route handlers. Все требуют входа; «кто» — минимальная роль. Роль проверяет RLS, прикладной слой дублирует проверку только для загрузки и импорта.

Всего 22 маршрута. Не включены: places, families, sources, tasks, event_types (обычный CRUD по шаблону, ещё ~15 маршрутов, генерируются одинаково) — [решение отложено, не считаю их в итоговую цифру].

Webhooks in/out: нет. Jobs: `anniversaries` (раз в сутки, считает ближайшие годовщины для S26, при желании письмо), `backup` (раз в сутки или неделю: GEDCOM + список файлов в приватное хранилище).

## The parts that bite

- **Раскладка дерева:** дети от нескольких браков, развод, приёмные, свёртка ветвей, бракосочетания между родственниками (циклы). Строить сначала простую раскладку «предки вверх, потомки вниз» с ограничением глубины; полный паритет с S02 — отдельный этап.
- **Названия родства на русском** («двоюродная тётя по матери»): правила рода и поколения, нужен собственный справочник; [2] только заявляет, что вычисляет.
- **GEDCOM:** версия 5.5.1 [9]; кодировки (UTF-8, ANSI/CP1251 у старых файлов — гипотеза для российских файлов), разные вендоры. Парсер писать самим или взять готовую библиотеку, оценить после теста на ваших реальных файлах. Отчёт о потерях обязателен (`gedcom_imports.report`).
- **Даты:** неточные, диапазоны, юлианские; в БД есть структура, разбор из текста («около 1717», «между 1811 и 1817») писать вручную.
- **Часовые пояса:** даты рождения — это календарные даты, не моменты времени; хранятся как `date`, а не `timestamptz` (исключение из общего правила, потому что иначе дата сдвигается). Отметки времени записей — `timestamptz`.
- **Идемпотентность:** импорт GEDCOM должен быть повторяемым без дублей: `gedcom_xref` и уникальный индекс `(tree_id, gedcom_xref)`.
- **Гонки:** две правки одной персоны → `version` и ответ 409.
- **Файлы:** лимит размера (например 20 МБ), типы JPEG/PNG/PDF; фото живых — только signed URL, срок жизни ссылки короткий.
- **Приватность:** публичный репозиторий и Pages — не место для живых людей; приглашения по одноразовой ссылке с хешем токена; `audit_log` для владельца.
- **Удаление и ПДн:** удаление персоны каскадом убирает её участие в событиях, документы остаются, пока не отвязаны; нужен диалог подтверждения.
- **Поиск:** `pg_trgm` по ФИО, достаточно для сотен записей.
- **Realtime и offline:** не нужны для семьи, не делаем.

## Build order

1. **Vertical slice** (грубо): вход по ссылке → создать дерево → создать персону (S09) → добавить родителя и ребёнка (F02) → увидеть простое дерево (S02). Экраны S01, S02, S09; таблицы trees, tree_members, persons, event_types, events, event_participants; маршруты: trees, persons, relatives, graph. Если слайс работает, стек подтверждён.
2. **Must-haves** по `features.csv`:
   - персоны и поиск: S01, фильтры;
   - события и роли: S10, S20, F03;
   - дерево с названиями родства: S02 полнее;
   - фото и документы: S04, S11, S21, F04;
   - страница персоны: S14;
   - экспорт: PDF (S24) и GEDCOM (S22);
   - импорт GEDCOM 5.5.1 (S23);
   - резервные копии;
   - роли и «только чтение» (F06);
   - конфиденциальность записей.
3. **Should-haves:** места и карта, источники, роспись (S15, S16), годовщины (S26), SVG/PNG/HTML, свёртка ветвей, отметки на фото.
4. **Could-haves:** задачи, диаграммы, роды, статистика.
5. **Fixes из replica-entrepreneur:** `/replica-entrepreneur` для Genery — публичные отзывы и форум; запускать после слайса, когда будет что сравнивать.
